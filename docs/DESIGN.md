# 设计取舍与踩坑记录

这份文档记录"为什么是这样做的"——包括几个真实踩过的坑。想改策略的话，先看这里。

## 1. 为什么要一个本地代理，而不是包装命令

最初的做法是 `jcodex`（一个包装脚本）：启动 codex 前先问一次 Jev，算出模型，再用
`-m <model>` 启动。问题是**一次启动只决策一次**：交互式会话里你接着输入第二个任务，
模型还是第一个任务的档位。

于是有了第二种模式：本地反向代理。Codex 的 provider 指向 `127.0.0.1:8787`，代理**每一轮**
都重新判断一次，并把 `model` / `reasoning.effort` 改写后再转发上游。两种模式都保留：

- `jcodex`：不需要常驻进程，适合脚本/CI 式的一次性任务
- `jcodex-live` / 常驻代理：适合交互式与 App（默认推荐）

## 2. 为什么用概率期望值，而不是取最高档

Jev 的 `score` / `choice` 回答带的是**概率分布**。第一版直接取分布里概率最高的档位，
并且"置信度低就升到最强档"作保险。结果第一句测试就翻车：

```
"把 README 里的错别字改一下"
  难度分布：fast 0.45 / balanced 0.35 / strong 0.20（Jev 置信度 0.55）
  → 取最高档 = fast，但置信度 0.55 < 0.60 → 按"保险"逻辑升到最强 → gpt-6-astra ❌
```

用最强模型改错别字，既贵又慢，完全违背初衷。改成两条：

1. **用期望值**（`Σ 概率 × 档位序号`）代替 argmax：上面这例期望≈0.55 档，落在 fast/balanced 之间，
   不会一步跨到最强。
2. **低置信度只上抬一档**（而不是顶到最强），且只对"综合分已经 ≥ 0.30"的任务生效——
   一句话指令天然"信息不全"，不能因为 Jev 说"需求不明确"就升级。

## 3. 权重为什么是这样

| 因子 | 权重 | 理由 |
| --- | --- | --- |
| 难度 | 0.60 | 主判据 |
| 深推理需求 | 0.25 | 区分"难"和"烦"：读十个文件拼接信息 ≠ 需要权衡多个方案 |
| 缺信息 | 0.05 | 故意压到很低，见上一条 |
| 轮数期望 | 0.10 | 需要多轮工具调用的任务通常更值得上强模型 |

阈值 0.30 / 0.60 / 0.85 是按实测校准的（见 README 的三条实测），都可配。

## 4. 一轮的任务指纹：怎么避免重复问 Jev

Codex 一轮对话会发多次请求（工具循环、重试、压缩上下文）。如果每次都问 Jev，
既慢又浪费。做法：

- 从 Responses 请求的 `input` 数组里取**最后一条 user 消息**
- 剥掉 `<environment_context>` / `<environment_details>` / `<user_instructions>` 等元数据块
  （否则任务文本会被这些噪声污染，判出来的档位偏高）
- 取 hash 作为"轮指纹"，用 64 条 LRU 缓存决策

于是同一轮里的后续请求直接复用决策；用户发新消息才会重新判。

## 5. 哨兵机制：怎么做到"我的选择优先"

代理不能无脑改写 `model`，否则你在 `/model` 里选的东西会被悄悄换掉。规则是
**只有请求模型命中哨兵集合时才改写**（默认 `gpt-6-astra`，加上虚拟的 `jev-auto`）。
选了别的模型 = 显式指定，代理原样放行，连 Jev 都不问。

## 6. 踩坑：顶层 `model` 被选择器写回，路由静默失效

装好一切、测试通过之后，某天发现有一轮请求的 `model=gpt-5.6-sol` **被原样放行了**。
查下去：`~/.codex/config.toml` 顶层的 `model` 从哨兵变成了 `gpt-5.6-sol`——
**App / CLI 的模型选择器会把你的选择写回这个文件**。于是代理老老实实"尊重你的选择"，
整条路由无声无息地失效，没有任何报错。

两个修法：

1. 顶层 `model` 直接设成哨兵自己（本项目用一个虚拟模型 `jev-auto` 来承担这个角色）：
   选择器写回的值和哨兵永远是同一个，两边再也不会错位。
2. `jcodex-doctor` 增加检查：顶层 model 不在哨兵集合 → 判 ❌，`--fix` 一键改回。

一般教训：**依赖"用户没改过某个键"的机制都不可靠**，要让机制本身对用户操作免疫。

## 7. 踩坑：不要改 App 包，要注入 `/models`

"在 App 里加一个选模型的按钮"最直接的想法是改 `app.asar` 注入 UI。放弃的原因：

- 破坏代码签名（Gatekeeper 可能直接拒绝启动）
- App 一升级就被覆盖，用户每次升级都要重打补丁
- 内部 IPC 协议是私有的，随版本变化

改成：App 的选择器本来就是拉 `GET /models` 渲染的，代理往响应里注入一个虚拟条目
`jev-auto`。不动 App 一个字节，升级后依然有效。实现要点：

- **克隆**已有条目的 JSON（字段 schema 完全一致，只是换了标识字段），避免字段缺失被拒
- **幂等**：已有同 slug 就不重复注入
- **防御式**：解析失败、结构不符 → 原样放行原字节，绝不把模型列表搞坏
- 顺手屏蔽 `If-None-Match` / 丢掉 `etag`，避免上游回 304 导致注入失效

## 8. 踩坑：WebSocket 与 hop-by-hop 头

代理最初把 `Upgrade` / `Connection` 当 hop-by-hop 头剥掉了（HTTP 代理的常规做法），
结果任何协议升级都会失败。而 Codex 里确实带 `tokio-tungstenite`，App 还有实时语音用的
`/live`。修法是识别 `Connection: Upgrade` 后改成**原生 TCP 隧道**：原样重放握手（含
`Upgrade` / `Sec-WebSocket-*`），然后 `select` 双向转发字节。
`test/test_ws.py` 用假 WS 上游（101 + echo）覆盖了这条路径。

另一个细节：客户端取消/切换一轮时会主动断开连接，`socketserver` 默认会打一整段堆栈到日志。
现在这类 `ConnectionResetError` / `BrokenPipeError` 被静默吞掉，日志保持干净。

## 9. fail-open 是硬要求

路由层不能成为故障点。所有异常路径都指向"照旧工作"：

- Jev 超时 / 报错 / 没 key → 代理 `keep`（原样放行，用你原本的模型）
- `jcodex` 启动器 → `JEV_FALLBACK`（默认 strong 档）
- 代理进程本身挂了 → launchd `KeepAlive` 拉起；应急 `codex -c model_provider=openai`
- 虚拟模型 `jev-auto` 是例外：它必须落到真实模型（否则上游收到未知模型名会报错），
  所以 Jev 不可用时它兜底到 strong 档

## 10. 图片规则的历史包袱

早期 Codex 目录里有不能读图的模型，所以写了硬规则"带图片 → 降到 fast 档"。
换了模型目录后这条规则变错了（四个 GPT 模型都能读图，带图提问可能是个难题）。
现在默认交给 Jev 正常判断，只有显式配置 `JEV_IMAGE_FORCE_TIER` 才强制换档。

教训：**硬编码的能力假设会过期**，能用配置表达的就别写死。
